## Problem

Two operator semantics are silently wrong (found reading the code; my probe hit a loud error first): `&&`/`||` produce **booleans**, not operand values (the compiler's `compile_short_circuit` pushes true/false), so `console.log(0 || 'dflt', 'a' && 'b')` prints `true true` (node: `dflt b`). And `==`/`!=` are lowered exactly like `===`/`!==`, so `'1' == 1` is `false` (node: `true`) and `null == undefined` can't be true.

## Success criteria

- [ ] `a || b` and `a && b` evaluate to the deciding operand, short-circuit, and match node for numbers, strings, `null`, `undefined`, objects and arrays (JS truthiness: `0`, `''`, `NaN`, `null`, `undefined` and `false` are falsy).
- [ ] `==`/`!=` follow the abstract equality algorithm for primitives (number/string/boolean/null/undefined); object-vs-primitive comparison is loud until objects have ToPrimitive.
- [ ] Crush's own `&&`/`||`/`==` are unchanged: JS-semantics ops only from the JS walker.

## Technical approach

- Lower JS `||`/`&&` to a value-preserving short circuit (`dup; truthy-test; jmp_if; pop; rhs`) or a `js.or`/`js.and` lowering; `==` to a `js.loose_eq` capability (one VM implementation, mirrored in AOT).
