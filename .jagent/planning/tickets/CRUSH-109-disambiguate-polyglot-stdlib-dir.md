# CRUSH-109 — Disambiguate the top-level `stdlib/` (polyglot) dir from the CRUSH-56/57 HostCap restoration work

| Field | Value |
|-------|-------|
| **ID** | CRUSH-109 |
| **Priority** | P4 |
| **Status** | Backlog |
| **Phase** | M9 |

## Problem

This repo has two entirely separate things both called "stdlib", with no
cross-reference between them anywhere in the planning docs:

1. `crates/crush-lang-sdk/src/stdlib.rs` — the real target of CRUSH-56/57:
   native Rust `HostCap` implementations (strings/math/conversion/collections,
   59 caps today), registered on the VM's capability registry, always available.
2. The top-level `stdlib/` directory — a *different* mechanism entirely: Crush
   modules generated by transpiling Rust/Python source through the polyglot
   walker pipeline (`source.(rs|py) -> walker -> CAST JSON -> stdlib/<module>.cast.json`),
   loaded at compile time via `import <module>`, executed natively by the VM with
   no subprocess. Currently 2 modules (`strings`, `patterns`), documented in its
   own `stdlib/README.md` with its own constraint table (a *different, narrower*
   set of supported constructs per source language than the main language itself).

Someone picking up CRUSH-56/57 cold could reasonably mistake `stdlib/` for the
restoration target, or not realize a second stdlib-delivery mechanism exists at
all. Neither `CRUSH-56`, `CRUSH-57`, nor any of the `CRUSH-88..97` shard tickets
mention `stdlib/`'s existence.

## Approach

1. Add a short cross-reference note to `stdlib/README.md` and to `CRUSH-56`'s
   file, each pointing at the other, naming the distinction (native HostCap vs.
   transpiled-CAST-module) explicitly.
2. Decide (dejavue decision, not silently) whether the two are meant to converge
   long-term (e.g. `import <module>` eventually resolving to native HostCaps for
   the caps that have them) or stay permanently separate mechanisms — CRUSH-56's
   restored caps and `stdlib/`'s transpiled modules should not silently drift into
   overlapping/conflicting names (e.g. a future `stdlib/strings.cast.json` vs. the
   native `str.*` HostCaps already covering overlapping ground — `contains`,
   `starts_with`, `trim`, `replace`, `substring`, `to_uppercase`/`to_lowercase` all
   already exist as both a `stdlib/strings.cast.json` transpiled module AND native
   `StrContainsCap`/`StrStartsWithCap`/etc. HostCaps today, with no documented
   precedence rule for which one `import strings` vs. a bare `str.contains(...)`
   call resolves to).
