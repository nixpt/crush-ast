## Why this exists

The CVM1 byte-slots for SPAWN (0x80), YIELD (0x81), and AWAIT (0x82) pre-date this ticket (they exist in `crates/crush-vm/src/bytecode.rs:95-97`), but they currently route through **direct handler arms** in `scheduler.rs:1241,1251,1254` and `portable_vm.rs:1136,1151,1157` — concrete semantics, NOT cap-call dispatch. There is **no `HostRequest` variant** for these opcodes (verified: `grep HostRequest::\(Spawn\|Await\|Yield\)` across `crates/crush-vm` returns 0 hits).

This means:

- The 5 execution tiers (interpreter / portable_vm / fastvm / AOT-Rust / AOT-C) implement SPAWN/YIELD/AWAIT independently with drift-prone direct arms.
- There is no `concurrency_native.<kind>` cap surface, so external callers cannot gate, mock, or test the cooperative-yield path through `HostCapsBuilder`.
- The `crush-diff` differential harness has no parametric TIGHT-pair coverage of SPAWN → `spawn()` / YIELD → `yield()` / AWAIT → `await()` opcode-byte → cap-gate resolution.

This ticket mirrors the **3-commit decomposition** of CRUSH-32 (AI) and CRUSH-33 (DOM): surface skew → cap-call seam → differential fixture.

## Out of scope (intentional non-goals)

- **Real concurrency backends** (thread pool, async runtime, event-loop driver, cooperative scheduler). Stubs are placeholders that produce self-documenting output until the real backends land in a later milestone. The surface shape AND the gate names (`concurrency_native.<kind>`) are stable; the implementation under those gates is what later milestones will swap.
- **OperandKind extending for SPAWN/AWAIT operands** (e.g., task_id for SPAWN, event_id for AWAIT, yield-count/duration for YIELD). The current `instruction_size()` lookup returns `OperandKind::None` for SPAWN/YIELD/AWAIT (existing pre-CRUSH-34 semantics — confirmed by the pre-existing direct arms at scheduler.rs:1241,1251,1254 and portable_vm.rs:1136,1151,1157, which take no operands). Real backends will need an operand-bearing model — captured as a Review forward flag below.
- **Frontend exposing `conc_<kind>(...)` or `concurrency_native.<kind>(...)` syntax.** Same deferred-comment note shape as AI/DOM.
- **Refactoring the existing pre-CRUSH-34 direct arms** in scheduler.rs / portable_vm.rs to use the new cap-call seam in Commit 1 — that work is Commit 2's scope (5-tier wiring). Commit 1 only adds the schema; it does NOT retarget existing arms.

## Reviewed forward flags (preemptive — for the per-commit code-reviewer rounds)

These are likely-to-come-up observations captured at the ticket level so the per-commit code-reviewer calls don't have to re-derive them.

1. **`concurrency_native_kind_for_opcode` complexity**: O(1) match on a constant byte with at most 3 arms (smaller than AI's 10 / DOM's 10). Same micro-cost — match on constant byte is O(1) for any arm count. Add the complexity rustdoc note (already mirrored from DOM in this commit).
2. **`stub_map` shape**: identical to AI/DOM (`{ok, kind, echo}`). No new claim needed — same macro. Do NOT include a "concurrency stub returns {ok, kind, task_id}" or similar claim (same trap the prior polish commit caught on DOM).
3. **Concurrency ops carry ASYNC semantics** that AI/DOM don't. SPAWN needs a task_id (future), AWAIT needs an event_id (future), YIELD needs a yield-count or duration (future). The current stub ignores all of these uniformly. The args-passing model will need extension when real backends land.
4. **Adjacency in `HostRequest`** (Commit 2): the CONCURRENCY_* family slots into the concurrency neighborhood near `Spawn { func: String }` / `Restart { task_id: usize }` / `Watchdog { task_id, deadline, action }` (the existing concurrency-adjacent variants). Adjacency to `Pause` (does-not-exist) is a design choice — keep `_ => None` catch-all on `concurrency_native_kind_for_opcode`.
5. **Commutative surface-parity check**: the `concurrency_native_kinds_constant_is_size_three_and_sorted_unique` test exists in BOTH `concurrency_native.rs` (Commit 1) and `differential.rs` (Commit 3). The Commit 1 version lives in `concurrency_native::mod tests`; the Commit 3 version is the surface-parity check that locks the differential fixture. Both reference the same `KINDS` const; no drift.
6. **SKIP-THINKER discipline**: Commit 2 (5-tier wiring) is non-trivial enough to spawn `thinker-with-files-gemini` once per ticket. Commit 1 (skeleton, the work of this turn) and Commit 3 (differential fixture, mechanical mirror) skip-thinker — schema fully locked.

## Notes from CRUSH-34 Commit 1 review (Nit Pick Nick)

Reviewer returned **LAND-AS-IS** with one substantive (non-blocking) follow-up recommendation:

- **`concurrency_native::KINDS` rustdoc muddle**: The `"surface-natural order wins"` framing in the KINDS rustdoc paragraph is muddled for concurrency because the byte-slot order (`SPAWN=0x80, YIELD=0x81, AWAIT=0x82`) DOES coincide with the KINDS order (`["spawn", "yield", "await"]`) — there is no tie-breaker being applied. Both candidate orderings happen to agree. The "surface-natural order wins" rule wording implies a disambiguation is occurring when none is. Suggested trim: *"for concurrency, the byte-slot order and the KINDS const order coincide, so no tie-breaker is needed."*

Captured here so a future CRUSH-34 review-flag polish commit (analogous to CRUSH-33's `08726d8`) has the rationale documented. Also useful as a forward-flag for any future concurrency-related ticket that adds ops beyond {_spawn_, _yield_, _await_} and needs to choose an ordering rationale.

## Process note -- 4-place ordering fix in Commit 1

The initial Commit 1 draft had `register()` body / macro instantiation list / both test cap-vecs in `[Spawn, Await, Yield]` order, but `KINDS` was defined as `["spawn", "yield", "await"]` (per the rustdoc claim). The validation basher caught a test failure at `spec_names_match_kinds_constant_in_order` with `left: "concurrency_native.await" right: "concurrency_native.yield"` (a `concurrency_native_cap!` macro invocation with cap-short-name `"yield"` was being placed at KINDS index 1, where `"await"` was expected). Fix: 4-place ordering swap -- swap `Await` + `Yield` in `register()` body, macro instantiation list, and both test cap-vecs to align all order-sensitive sites with the KINDS contract. Post-fix: 7/7 GREEN.

Diagnostic lesson: the `spec_names_match_kinds_constant_in_order` test (and its DOM/AI twins) is a *positive invariant test* on top of the size+no-dup *positive invariant test* -- both are needed to catch both kinds of drift (count-type and order-type). Both Compile green and Test green matters here; a tight `test result: ok` filter that misses per-thread FAILED output can swallow order-type test failures (that's why the validation basher prompt this turn explicitly required `tail -30` of the full cargo test output, not just the `test result:` line).
