## Problem

The `ts` path strips basic annotations and `interface` correctly. But `TsEnum`/`TsModule` (namespaces) are **dropped** (lower_swc.rs ~434 `return Ok(None)`), so `enum C { R, G } console.log(C.G)` fails later with "load from uninitialised slot". `import type` lowers like a value import, and `TsImportEquals`/`TsNamespaceExport` become a no-op comment. Note: node's default type stripping rejects enums and namespaces too; they need `--experimental-transform-types`, so use that flag for the `.out` of those programs. The rest of TS's type-only surface is unmeasured.

## Success criteria

- [ ] Every type-only construct is erased and the program matches `node file.ts`: type aliases, generics (`f<T>(x: T)`), `as`, non-null `!`, `satisfies`, optional params `x?:`, access modifiers on params, `readonly`, `declare`, `import type`, abstract-only members.
- [ ] `enum` (numeric and string, reverse mapping for numeric) and `const enum` match node.
- [ ] Constructs node's type stripping rejects (namespaces with values, parameter properties, decorators, legacy `module`) are loud with a clear message, matching node's own refusal.
- [ ] The TS corpus twin (from CRUSH-zorro-4) passes for every JS area that passes.

## Technical approach

- Lean on swc's TS strip transform where possible instead of hand-erasing; enums lower to an object literal (needs CRUSH-zorro-16's objects).

## Files to modify

## Non-goals

- Type checking (out of scope by design: node doesn't type-check either).
